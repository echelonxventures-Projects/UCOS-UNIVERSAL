# `spec/` — Machine-readable UCOS definitions

These are the **source files engines and CI consume**. The universe constitutions (`../constitutions/`) explain *why*; this folder states *exactly what*. If they disagree, the CI check fails until both agree.

## Run the checks

```bash
tools/ci.sh                            # everything, as CI runs it
tools/ci.sh --fix                      # regenerate manifests, registries and contracts first
python3 tools/ucos_check.py            # just the spec checker; exit 1 on errors or mandatory gaps
python3 tools/ucos_check.py --write    # also refresh golden expected blueprints and gap reports
```

What `ucos_check` verifies today:
1. Every `*.schema.json` is a valid JSON Schema 2020-12. Every manifest and platform definition validates against its schema.
2. **Sole ownership (L4):** no object type or event has two providers.
3. Every `requires`, `optional` and `implements` reference resolves. Adapters implement an abstract port. No capability requires one from a later phase.
4. Every consumed event has a producer. Every control referenced by manifests and regulations exists, and every control implementer exists.
5. **Temporal rule (ARCH-TMP-05):** every capability that uses Temporal services has `temporal.core` in its requires-closure. Kinds agree with `constitutions/TEMPORAL-BINDING-MATRIX.md`.
6. Every manifest's universe has a constitution folder.
7. **Reference composition** of each golden platform definition, following the semantics of `rules/core/closure.dl`:
   - base capabilities, plus channel requirements, plus the dependency closure;
   - applicable regulations, then controls, then implementing capabilities, iterated to a fixpoint;
   - adapter selection per jurisdiction and method (specific jurisdiction beats `*`);
   - gaps: missing capability or adapter, an excluded capability that is required, phase not available, controls not implemented, missing simulators for external-I/O ports, consumed events without a producer in the blueprint.
8. **Determinism (L18):** the same inputs give the same blueprint hash.
9. **Gates:** every gate id referenced in any document or manifest (e.g. `ARCH-TMP-05`, `SEC-*`) is defined in `certification/gates.yaml`; gate profiles reference only known gates.
10. **Registries in sync:** `registries/errors.yaml` and `object-types/` equal what `tools/gen_registries.py` derives from the current specs and manifests.

## Generated registries: what they are and are not
- **Object-type schemas** are skeletons. Each one extends the canonical envelope and types its attributes from the constitution's notation: value types (`TimePoint`, `Money` …) become `$ref`s, and `a|b|c` becomes an enum. Other attributes are carried untyped, with the spec text as their description. 37 types are defined only in prose or YAML examples and are flagged `"attributesFromSpec": false`. The constitutions remain normative. Stewards tighten the schemas as the DDL generator (`gen.ddl.postgres`, U59) is built.
- **Error categories** come from name heuristics (`derived: heuristic`). A steward confirms each one when its universe's API is implemented. Responses use RFC 9457 `application/problem+json` with `code` set to the registry code.
- **Derived manifests** (maturity `experimental`) list the objects, commands, queries and events named in the spec. `requires` comes from *Depends on*; dependencies in a later phase, or ones that would close a cycle, become `optional`. A steward replaces each derived manifest with a hand-authored one (adapters, decisions, controls, views) before that universe's phase starts.

## What is not here yet (generated later by the build)
- OpenAPI, AsyncAPI and GraphQL files. These are generated by U63/U61 from the manifests at blueprint activation.
